## P1-11 — runtime/referee evidence and validator/execution identity can be self-asserted inside a valid receipt
DISPOSITION: ACCEPT
Rationale: `experiments/breadth/crates/work_receipt_contract_v1/schema.json` requires only `runtime_evidence` (properties `execution_log`, `model_used`, optional `tokens_in`/`tokens_out` — schema.json lines 86-109) and `referee_spec_sha256`/`referee_result` (enum `["PASS","FAIL"]`, lines 115-124). There is no dispatch-receipt hash, call-ledger, raw-provider-result field, adapter/runtime identity, candidate-tree hash, acceptance stdout/stderr/exit binding, cleanup receipt, validator-implementation hash, or canonical self-hash of the receipt anywhere in schema.json or `validate.py`. `validate.py`'s `WorkReceiptValidator` checks only the 7 rejection classes named in the card — none touch `runtime_evidence` content or bind it to independently verifiable execution proof. A receipt with `"runtime_evidence": {"execution_log": "x", "model_used": "y"}` and `"referee_result": "PASS"` passes every rejection check as long as the `*_sha256` fields are well-formed hex, regardless of whether those hashes correspond to real bytes.
Proposed amendment / rebuttal: Not closed. Proposed negative-witness fixtures: `fixtures/rejection_unbacked_referee_result.json` (referee_result=PASS with no verifiable referee-receipt hash) and `fixtures/rejection_self_asserted_runtime_evidence.json` (execution_log path that resolves to nothing). Card amendment: add required fields `referee_receipt_sha256` (distinct from `referee_spec_sha256`), `dispatch_receipt_sha256`, and a canonical `receipt_self_sha256` computed over the receipt's own canonicalized bytes minus itself.
Cost/benefit: Proportionate now — this is schema/validator work on an already-blocked-pending-smoke crate, $0, no live call required. Under S*, worth doing before any operator unblocks implementation beyond the validator.

## P1-13 — `ERROR` can satisfy the negative run without proving rejection semantics
DISPOSITION: PARTIAL-ACCEPT
Rationale: `gastown_tier_run_smoke_v1/010.100.TASK.md` lines 59-64 ("Negative run... must produce `REJECTED` or `ERROR`, preserve diagnostics, and leave the Bead open or explicitly blocked") verbatim matches Sol's citation — the smoke card's own negative-gate text is genuinely loose exactly as described. But the machinery the smoke's Phase 2 acceptance run will actually invoke is already more disciplined: `referee_kernel_contract_v1/witnesses/w5_acceptance_failed_rejected/witness.py` asserts `receipt["state"] == "REJECTED"`, `receipt["acceptance"]["returncode"] != 0`, and that both `stdout_path`/`stderr_path` artifacts exist on disk — failed acceptance is proven to produce a specific `REJECTED` state with preserved diagnostics, not an undifferentiated exit. Separately, `w2_scope_escape` and `w6_verifier_mutated_candidate` show `ERROR` is reserved for integrity violations, each bound to a distinct `ReasonCode` via `reasons.py`'s `classify()` — `ERROR` is itself a closed, reason-bound class in the underlying kernel, not a catch-all.
Proposed amendment / rebuttal: Tighten the smoke card's negative-run prose to require the specific `REJECTED`/`acceptance.returncode != 0`/preserved-diagnostics proof `w5` already demonstrates, rather than accepting bare `ERROR` as a pass: "The negative run must terminate `REJECTED` with `acceptance.returncode != 0` and preserved stdout/stderr; an `ERROR` outcome is a FAILED gate requiring adjudication, not an acceptable negative witness, per referee_kernel_contract_v1 w5/w6." No new fixture needed in referee_kernel_contract_v1 itself — w5 already is the required negative witness; the gap is purely in the smoke card's acceptance language.
Cost/benefit: Cheap, $0 card-text fix. Moot for the current PARTIAL seal — Phase 2's negative run never executed, so this finding is prospective, not a defect in anything shipped.

## P2-01 — "scan all string values" is neither a credential type system nor a complete witness
DISPOSITION: PARTIAL-ACCEPT
Rationale: `policy_kernel_contract_v1/010.100.TASK.md` line 46 ("validator scans all string values") is accurately characterized. `validate.py`'s `CREDENTIAL_PATTERNS` is a keyword-regex blacklist (`key`, `secret`, `token`, `password`, `auth`, `credential`, etc.), applied recursively over strings only — no concept of byte arrays, encoded/split tokens, file/secret-store locators, or diagnostics/serialization scanning. The committed fixture `fixtures/invalid_credential_in_field.json` demonstrates the validator DOES catch the labeled case, but there is no fixture demonstrating detection of a bare secret-shaped value without a trigger keyword, nor of a split/encoded token — the demanded negative witness for those cases does not exist.
Proposed amendment / rebuttal: Add `fixtures/invalid_credential_no_keyword.json` (a raw high-entropy secret-shaped string with no trigger word — documents that it currently PASSES) and `fixtures/invalid_split_token_credential.json` (token split across two evidence_refs entries). Card amendment: "The credential scan is a keyword heuristic, not a type system; secret-shaped values without trigger words are a known, accepted gap pending a stronger detector or typed secret-reference design."
Cost/benefit: Proportionate at fixture-level (documents the known gap at $0); a full entropy/typed-secret detector is disproportionate for a policy kernel that never invokes a model or holds credentials — blast radius of a false negative is bounded by the kernel's own design.

## P2-02 — determinism and temporal canonicalization are internally ambiguous
DISPOSITION: ACCEPT
Rationale: `policy_kernel_contract_v1/010.100.TASK.md` lines 35-36 and 65-67 match Sol's citation exactly — two separate detachable-field exceptions to determinism (`decision_id`, `observed_at`). `validate.py`'s `verify_decision_id_deterministic` checks decision_id format and, only if all three input hashes are explicitly supplied by the caller, verifies exact derivation — otherwise it only rejects obvious timestamp patterns. Proposed amendment / rebuttal: Not closed. Card amendment: "Canonicalization: decisions MUST be serialized via a frozen canonical profile before hashing; `decision_id` verification against input hashes is mandatory, not optional, at referee time; the policy implementation's own source hash MUST be bound into a `policy_impl_sha256` field." Add fixture `fixtures/invalid_undetermined_id_unverified.json` showing the current validator accepts a decision_id it cannot actually verify when hashes aren't supplied.
Cost/benefit: Proportionate — exactly the kind of authority-bearing-object ambiguity S* says cheap-hand work should close before implementation beyond the validator is unblocked; cheap now, expensive to retrofit once decisions are consumed by real dependents.

## P2-03 — a closed reason enum can still conceal the controlling failure
DISPOSITION: PARTIAL-ACCEPT
Rationale: `referee_kernel_contract_v1/reasons.py`'s `classify()` maps text to exactly one `ReasonCode` and explicitly refuses to coerce ambiguous cases — returns `None` when zero or more than one signature matches, per its own docstring: "an unrecognized or ambiguous failure is never coerced into a code; callers must treat None as WITNESS-BLOCKED, not as a pass." This is a real, cited mitigation against Sol's hostile scenario. However, no fixture or witness in `witnesses/w1`-`w7` constructs a genuine multi-fault case to prove `tier_runner.core` actually emits both signature substrings rather than short-circuiting on the first-detected fault. Also confirmed: there is no `schema.json` in this crate at all (only `reasons.py`, a Python enum) despite the card's line 29 claim "Reason codes are a CLOSED enum frozen in the schema" — and `work_receipt_contract_v1/schema.json` has no `primary_reason`/`reasons[]` field referencing `reasons.py`'s codes at all.
Proposed amendment / rebuttal: Add witness `w8_multi_fault_scope_and_acceptance` constructing a candidate with both a scope violation and a failing acceptance command, asserting `classify()` returns `None` (WITNESS-BLOCKED) — this would upgrade the finding to REJECT if it passes. Add `primary_reason`/`reasons[]` fields to `work_receipt_contract_v1/schema.json` bound to `reasons.py`'s enum, and author the missing `schema.json` for the referee kernel to match the card's own claim.
Cost/benefit: Proportionate — one new witness at $0 would resolve most of the open question; the schema-binding gap between the two crates is a real cross-crate integration gap worth closing before either crate's validator-only status is lifted.

## P2-04 — `external_refs` uses a field-name blacklist where a closed descriptive type is required
DISPOSITION: PARTIAL-ACCEPT
Rationale: `work_receipt_contract_v1/schema.json`'s `external_refs` definition is already a closed tagged union, not a blacklist — `additionalProperties: false` with exactly four allowed string-typed keys (`bead_id`, `gas_town_rig`, `worker_identity`, `agent_deck_session`), none named `verdict`/`status`/`result`. This structurally forecloses Sol's illustrative attack at the schema level. BUT `validate.py` never loads or enforces `schema.json` at all — the actual enforced gate is `_check_external_override_verdict`, which only rejects a **nested dict value** containing a `verdict` key. The committed fixture `fixtures/rejection_external_override_verdict.json` exercises exactly that narrow case. A hostile string value in any of the four allowed fields — e.g. `"worker_identity": "status: ACCEPTED, close this bead"` — passes both the (unenforced) schema and the actual validator, since no content-scanning exists on these free-text string fields. This is precisely Sol's prompt-injection/verdict-synonym scenario.
Proposed amendment / rebuttal: The closed field-name union already exists in design but isn't wired in, so the specific "add a verdict field" attack is REJECTable once schema enforcement is actually active. Two fixes needed: (1) wire `jsonschema.validate` against `schema.json` into `validate.py` (currently absent entirely — a latent defect independent of Sol's finding); (2) add content restrictions to the four `external_refs` string fields, plus fixture `fixtures/rejection_external_ref_prompt_injection.json`.
Cost/benefit: High priority relative to its cost — wiring the already-written schema.json into validate.py is nearly free and closes a real enforcement gap (not just a Sol-hypothetical one); the content-restriction half is a small addition.

## P2-05 — task, attempt, repository, time, and path identities are not portable namespaces
DISPOSITION: ACCEPT
Rationale: `work_receipt_contract_v1/schema.json` defines `task_id`/`attempt_id` as bare strings with no namespace/authority-domain field; `base_commit` is a bare 40-hex-char pattern with no repository-identity or object-format field alongside it; `created_at` is a bare ISO 8601 string with no distinction between self-asserted and independently-observed time, matching Sol's characterization exactly. `referee_kernel_contract_v1/witnesses/w3_base_commit_drift/witness.py` confirms `base_commit` is checked only within a single repo — no cross-repository disambiguation anywhere in the crate. `predecessor_receipts` is at least content-derived (SHA256 pattern), the one piece of portable identity already present; task/attempt/repository identity are not.
Proposed amendment / rebuttal: Not closed. Card amendment: add `authority_namespace`, `repository_object_format` (e.g. `"git-sha1"` vs `"git-sha256"`), and split `created_at` into `observed_at`/`recorded_at` with a `time_source` field. Proposed fixture: `fixtures/rejection_cross_repo_task_id_collision.json` — two receipts with identical `task_id` but different (hypothetical) `authority_namespace`, currently indistinguishable by the schema.
Cost/benefit: Proportionate given the card's own explicit multi-scheduler design goal ("replace Beads tomorrow without rewriting historical evidence") — namespace collision is a real risk precisely because the contract is designed for portability across schedulers/repos; cheap to add now while the crate is still validator-only.

## P2-06 — phase 1 lacks the hostile transport matrix needed to prove "no shell reinterpretation"
DISPOSITION: ACCEPT
Rationale: Fully confirmed by direct inspection. `gastown_tier_run_smoke_v1/phase1/selftest.py` invokes `capture_fixture.py` with exactly one hardcoded, entirely friendly argument set — no spaces, quotes, newlines, leading dashes, Unicode, CRLF, shell metacharacters, percent expansion, empty strings, or duplicate flags. `verify_capture.py` only checks that each required flag is present in `argv` and followed by a non-`--`-prefixed value — it does not validate byte-exact preservation of hostile content. This is precisely "one friendly argument capture," not a hostile matrix. Compounding this: `phase1/TRANSPORT_LOG_NATIVE_20260719.md`'s own verdict confirms the fixture was never even exercised through the real `gt` transport path, so even the friendly self-test's assurance about `gt`'s actual argument transport is unproven.
Proposed amendment / rebuttal: Not closed, and constructible entirely at $0 without any live dispatch or daemon — needs only `capture_fixture.py` invoked directly with hostile argv content, no `gt`/`bd` involved. Proposed additions to `phase1/selftest.py`: cases for embedded spaces, embedded double quotes, newlines, a leading-dash task-text value, Unicode, CRLF, shell metacharacters, percent expansion, empty-string values, and duplicate flags — each asserting `verify_capture.py` recovers the byte-exact original value. Card amendment: define "substantive wrapper logic" as any logic beyond argv pass-through and out-path redirection; require vendored doc excerpts to preserve surrounding constraint sentences, not only the favorable one.
Cost/benefit: High priority, very cheap — pure Python argv testing against an already-committed fixture, gated on nothing (not even Phase 1's DAEMON-REQUIRED seal, since it bypasses `gt` entirely). Should be closed before any Phase-1 retry protocol is authorized.
