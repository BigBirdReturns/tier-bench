# Anchor Crate Science Program

## Inheritance

The program inherits the causal test from the Terra–Sparx and Luna anchor experiments: destroy the live planner, preserve only the sealed anchor and typed receipts, start a fresh controller or planner, and determine whether accepted work continues. The home-lab extension replaces one fixed worker surface with a backend-neutral DAG and executor ABI.

## Experiment 0: contract and fixture floor

The committed fixture floor proves:

- the DAG is acyclic and deterministic;
- the task identity is backend neutral;
- CUDA and RISC-V lowerings produce distinct execution identities;
- both fixture executors produce validator-equivalent accepted products;
- the controller, rather than the executor, owns hashes and acceptance;
- controller replacement succeeds from a sealed anchor;
- continuation without the anchor fails;
- tampered anchors and artifacts fail;
- undersized backend memories cannot be combined into fictional pooled capacity.

This is software-contract evidence, not hardware evidence.

## Experiment 1: physical RTX 4060 canary

The first real backend is the already deployed utility route because it supplies the smallest legible physical transaction. It is admitted only after PR #52 produces a complete three-host census and a qualified exact Qwen function. The backend manifest binds:

```text
control-host observation and census receipt
RTX 4060 UUID, PCI identity, memory, driver, and power limit
Python and nvidia-smi executable identities
loopback-only dedicated Ollama process
Ollama version
qwen3.5:9b-q4_K_M model digest, size, quantization, and residency
physical executor and lowering digests
```

The launcher runs the unchanged physical-availability cartridge with only `generate_decision_packet` placed on the 4060. The deterministic host retains normalization, state derivation, validators, acceptance, artifacts, receipts, and anchor advancement. A passing smoke requires the exact source-bound conclusion and human-review requirement, not a successful model process or fluent summary.

## Experiment 2: stock RTX 3090 burst backend

Replace the 4060 route with the exact Dell RTX 3090 and Core X treatment:

```text
head identity
Thunderbolt controller and port
Core X enclosure and cable
GPU UUID and VBIOS
Windows or Linux driver
runtime and build
model and quantization
power limit
lowering implementation
```

Run the same admitted cartridge at 225 W, 250 W, and 275 W. Record cold hydration, time to first accepted product, warm node latency, wall energy, GPU energy, memory temperature, core temperature, throttle state, host traffic, SSD traffic, failure recovery, and accepted outcome.

The selected profile is the lowest complete point on the accepted-work Pareto surface. Stock operation remains mandatory during the return window. Thermal-pad modification requires a measured thermal or throttling defect.

## Experiment 3: head substitution

Run one physical accelerator cartridge through at least two qualified heads. Preserve the semantic cartridge and portable task identity. Require new plan and execution identities for every changed head, driver, runtime, port topology, or power envelope. The anchor and accepted artifacts must survive the head transition.

## Experiment 4: accelerator substitution

Run the same candidate node through materially different backends:

```text
RTX 4060 Qwen/Ollama utility route
RTX 3090 CUDA burst route
CPU or portable llama.cpp fallback
RISC-V or custom-accelerator implementation
optional remote open-weight control
```

Use the same cartridge and controller validators. Compare accepted work, energy, time, intervention, failure, and recovery. A backend wins a task node rather than an abstract benchmark category.

## Experiment 5: task-family widening

After one cartridge passes under forced controller replacement and physical backend substitution, widen to the five MENACE witness families:

1. physical availability;
2. cooperative handoff;
3. multi-role handoff;
4. partitioned controller supervision;
5. stack recovery and substitution.

The widening unit is a new cartridge with its own independent acceptance, not additional prompt-size cells for the original task.

## Kill conditions

Hold or reject the architecture when:

- the candidate output cannot be validated independently;
- verification consumes more human attention than the task saves;
- a backend’s removal loses task state or accepted evidence;
- fallback silently changes task or authority semantics;
- useful execution requires undisclosed memory pooling;
- the same cartridge cannot be lowered without backend-specific task edits;
- GPU or WAN loss removes the survival substrate;
- hardware energy and heat do not buy accepted work.
