1. **Line 16, `merge_intervals`** — Touching intervals are not merged because the merge condition uses strict `cur[0] < last[1]` instead of `<=`, contradicting the module's own stated rule and worked example ("[1,2] and [2,3] ... should merge"). Input: `merge_intervals([[1,2],[2,3]])` returns `[[1,2],[2,3]]` instead of the documented `[[1,3]]`.

2. **Lines 13 and 17, `merge_intervals`** — `merged = [s[0]]` keeps a reference to the caller's original interval objects (since `sorted()` doesn't copy the inner lists), and `last[1] = max(last[1], cur[1])` then mutates that object in place. This corrupts the caller's input data as an unintended side effect, even though the docstring implies a fresh, non-destructive result ("return a new sorted list"). Input: `data = [[1,5],[3,8]]; merge_intervals(data)` — afterward `data[0]` has silently become `[1,8]`, destroying the original `[1,5]`.

3. **Line 17, `merge_intervals`** — The function assumes interval elements support item assignment (i.e. are lists), unlike every other function in the module (`contains_point`, `max_non_overlapping`, `busiest_point`), which accept any 2-item sequence via `for s, e in intervals` unpacking. Passing tuples crashes. Input: `merge_intervals([(1,3),(2,5)])` raises `TypeError: 'tuple' object does not support item assignment`.

4. **Line 31, `contains_point`** — Uses strict inequalities `s < p < e`, excluding both endpoints, directly contradicting its own docstring, "endpoints included." Input: `contains_point([(1,5)], 1)` returns `False` even though 1 is the interval's own start point; likewise `contains_point([(5,5)], 5)` returns `False` for a degenerate single-point closed interval that trivially contains 5.

5. **Line 41, `max_non_overlapping`** — Sorts candidates by interval start (`x[0]`) instead of by end (`x[1]`), which is the wrong key for the classic greedy interval-scheduling-maximization algorithm and can pick a "greedy-blocking" first interval, yielding a suboptimal count. Input: `max_non_overlapping([(1,10),(2,3),(4,5)])` returns `1` (blocked by the wide `(1,10)` chosen first), but `(2,3)` and `(4,5)` are mutually non-overlapping, so the correct maximum is `2`.

6. **Line 45, `max_non_overlapping`** — Uses `cur[0] >= end` to admit a candidate as non-overlapping, which treats exactly-touching intervals as compatible/selectable. This contradicts the module's explicit rule that touching intervals count as overlapping (should be strict `cur[0] > end`). Input: `max_non_overlapping([(1,2),(2,3)])` returns `2` (counts both touching intervals as a valid selection) though per spec they overlap and only `1` should be selectable.

7. **Line 25, `total_covered`** — Computes covered length as `e - s` rather than `e - s + 1` for closed integer intervals, undercounting the true covered length by one unit per merged segment. Input: `total_covered([(1,1)])` returns `0`, even though the single-point closed interval `[1,1]` unambiguously covers one integer (the point 1), so the correct covered length is `1`, not `0`.
