# 700.100 RECEIPT — amortization_v1

**Question:** does desk-mode ceremony pay off when ONE driver visit dispatches SEVERAL
hands, versus separate plain sessions? Three equal-small tasks (different files, no
conflicts): T1 `burn_report.py --min`, T2 `crate_new.py --list`, T3 `dispatch.py --dry-run`.

**Date:** 2026-07-18. All sessions `claude -p --model fable --output-format json`,
headless, launched from the experimenter session, run sequentially. Scripts reset to
the same git baseline before each arm. Measured from each session's output JSON
(`total_cost_usd`, `num_turns`) and the last usage row of its transcript
(`input_tokens + cache_read_input_tokens + cache_creation_input_tokens`).

## Verdict

Amortizing the ceremony across three tasks in one driver visit **did not beat Arm D on
cost but did beat it on context**: C's completed run cost $4.73 all-in versus D's
$2.82 (C is 1.67× more expensive; even the driver session alone, $4.29, loses), while
C held one 79k-token context versus D's 135k summed across three sessions (~42% less
total context, i.e. the ceremony read/setup is genuinely paid once instead of three
times). That puts S* — the task size where crating beats payload-inline — **above
"three T1 tasks bundled per visit" on the driver axis at fable rates**: the driver's
adjudication turns dominate cost, so N=3 amortization of tiny tasks still loses to
plain sessions on dollars, and the win shows up only in quota-relevant context
compression. Consistent with the CRATE_OPS routing law (don't crate what a cheap call
solves inline); the desk should pay off only for bigger tasks, larger N, or when hands
land on another vendor's quota. Caveats, all real: K=1 replicate per arm, no variance
estimate; tasks are tiny (T1-scale flag additions), which is the regime the routing
law already says favors D; both arms ran fable — D is fable doing bulk at frontier
rates (the doctrine would route those to ~$0.07–0.13 haiku calls, which would make D
cheaper still), so this does not measure the doctrine's intended cheap-hand D either;
`PowerShell` was added to `--allowedTools` for **both** arms (deviation from the spec'd
flag list, required on Windows); D2 and D3 found Arm C's leftover frozen specs/referees
in the tree and validated against them (contamination that made D's targets sharper at
C's authoring expense); C's turn count includes synchronous dispatch-wait turns; runs
were sequential, so C's potential wall-clock win from parallel hands is unmeasured; and
the two failed C attempts are excluded from the headline but are themselves evidence
that headless desk-mode is operationally fragile.

Nothing committed or pushed. Working-tree residue: the three implemented flags +
tests (Arm D's versions, last writer), and Arm C's crates under
`experiments/breadth/crates/{burn_min_v1,crate_list_v1,dispatch_dryrun_v1}/`.
